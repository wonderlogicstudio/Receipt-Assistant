# 날짜별 누적 저장과 모바일·PC 연결 설계안

작성일: 2026-10-18. 상태: 설계 정리, 미구현.

관련 문서: [통일 양식](receipt_standardization_proposal.md), [상호 보정](merchant_resolution_design.md). 이 문서는 저장 구조 변경 제안이다. DB migration, 기존 자료 수정, 과거 작업 재검수/재출력, 모바일 앱, 로그인, 결제, 서버 배포, 자동 삭제를 실행하지 않는다.

## 1. 현재 구현과 목표

| 항목 | 현재 | 목표 |
|---|---|---|
| OCR 후 결과 | Streamlit 현재 세션의 검수 목록에 보관 | 스캔한 건마다 미검수 상태로 지속 저장 |
| 새 업로드 | 현재 검수 목록을 새 결과로 교체 | 새 거래 후보 추가 또는 기존 거래의 새 처리 시도로 연결 |
| SQLite 적재 | 엑셀 생성 시 처리 이력·레코드 저장 | 저장과 엑셀 생성을 분리 |
| 중복 검사 | 전달받은 배치 목록 안에서 비교 | 작업공간의 기존 날짜별 자료와 중복 의심 관계 관리 |
| 과거 이력 | 작업별 읽기 전용 조회·기존 엑셀 재다운로드 | 명시적 재검수와 새 버전 출력은 후속 별도 기능 |
| 모바일·PC | 공통 사용자 저장소·동기화 없음 | 같은 영수증ID와 수정버전을 사용 |

기존 `processing_jobs`는 업로드/처리 묶음의 이력이며 날짜별 영수증 원장과 동일하지 않다. 과거 엑셀 재생성이나 실제 장부·신고 기능을 이번 설계로 구현된 것처럼 설명하지 않는다.

## 2. 저장·처리 역할

```text
모바일 촬영 / PC 일괄 업로드
-> 파일 출처와 수신 작업 식별
-> OCR 처리 시도 -> 표준 OCR 결과 -> Parser/Validator
-> 영수증 미검수 기록 저장
-> 같은 기록을 모바일/PC에서 조회·검수
-> 거래일자·통화별 조회 -> 선택한 수정버전의 엑셀 생성
```

정식 구독 서비스의 기준 저장소는 공통 서버로 두는 방향이다. 모바일은 아직 서버가 수신 확인하지 않은 입력을 제한적으로 대기시킬 수 있지만 무제한 원본·전국 상호 DB·전체 이력을 기기에 복제하지 않는다. 기기 캐시는 기간·용량·전송 완료 후 정리 정책이 필요하다.

스캔 직후 로컬 대기와 서버 저장을 구분해 표시한다. 서버의 지속 저장 확인 전에는 '서버 저장됨'으로 표시하거나 유일한 원본을 자동 정리하지 않는다. 오프라인 입력도 대기 한도와 실패/재시도 상태를 보여주며 기기 분실·브라우저 초기화에 대한 백업으로 설명하지 않는다.

OCR은 휴대폰/PC/외부 API/서버 중 선택 가능하고, 파싱·검증·엑셀 생성은 공통 엔진을 활용한다. GPU는 처리량·대기시간 측정 후 결정한다. 현재 로컬 검증은 SQLite로 설계 계약을 확인할 수 있으나 그대로 인터넷에 공개하지 않는다.

## 3. 논리 저장 단위

아래는 테이블명/DDL 확정이 아닌 책임 구분이다. 실제 스키마·migration은 후속 작업으로 작성한다.

| 저장 단위 | 주요 필드·책임 |
|---|---|
| 영수증 현재값 | `scope_id`, `receipt_id`, `revision`, 통일 양식의 선택값, 검수상태, 생성/수정 시각 |
| 원본 출처 | 파일ID, 내부 파일 해시, 페이지/거래 구역, 파일명, 수신 채널, 보관만료시각, 원본가용상태. 원본 바이너리와 분리 |
| OCR 처리 시도·관측값 | attempt ID, Provider/Adapter/Parser/Validator 버전, 처리상태·진단코드, 허용된 구조화 후보·근거ID. raw text/raw JSON 전체 저장 금지 |
| 검수 수정 이력 | 이전/다음 revision, 허용 필드의 변경 전후 값, 변경이유·시각·작업자 식별. 개인 연락처·원문을 이력에 우회 저장 금지 |
| 결제·차감 상세 | 카드/현금/포인트/상품권 등 여러 행, 포인트 역할, 단위/환산 명시액, 할인 포함관계, 원본 근거 |
| 관계 | 중복 의심, 동일 거래 증빙, 취소/환불/상품권 구매·사용 연결. 사용자 검토 상태 포함 |
| 엑셀 출력 스냅샷 | 대상 거래일 범위·통화·필터, receipt ID/revision 목록, 양식 버전, 생성시각, 파일 가용상태, 무결성 해시 |
| 수신·동기화 작업 | scope/client record/operation ID, 요청 내용 해시, 수신 상태, 기대 revision. 재전송·충돌 추적 |

`scope_id`는 로컬에서는 단일 작업공간 식별자다. 사업장/사용자별 공개 운영에서는 권한검사를 서버에서 시행해야 하며 ID 필드만 추가해 접근이 분리된다고 주장하지 않는다. 상호 사전과 개인 영수증 이력을 같은 공개 데이터로 취급하지 않는다.

## 4. 반복 전송과 중복 의심

1. 같은 작업공간의 같은 operation ID·같은 내용 재전송은 기존 처리 결과를 반환한다. 거래를 추가 생성하지 않는다.
2. 같은 operation ID인데 내용이 다르면 충돌로 반환하고 기존 값을 덮어쓰지 않는다. 원장 저장과 수신 확인은 같은 DB transaction으로 반영한다.
3. 같은 receipt ID의 재OCR은 새 attempt를 만들고 이전 사용자 선택값은 유지한다. 자동 후보만 갱신하고 선택값 갱신은 명시적 검수 수정으로 남긴다.
4. 동일 파일 해시는 중복 업로드 의심 또는 같은 출처 재사용 신호다. 한 PDF/사진 안의 여러 영수증은 구역별 거래가 될 수 있으므로 파일 해시만으로 비용 기록을 병합하지 않는다.
5. 다른 사진으로 찍은 같은 영수증은 해시가 다를 수 있다. 날짜·시각·상호·사업자번호·금액·수단 등의 근거로 중복 후보를 제시한다. 같은 날짜·금액·상호만으로 자동 삭제/병합하지 않는다.
6. 상세영수증·카드전표·세금계산서가 같은 거래인지 검토 후 주 기록과 보조 증빙을 연결한다. 여러 증빙을 비용 여러 건으로 합산하지 않는다. 연결 전에는 중복의심 건수와 잠재 중복 금액을 표시한다.
7. 취소/환불은 원본 기록 삭제가 아닌 별도 관계 기록이다. 부분환불·다른 달 환불을 지원하는 계약을 먼저 정하고, 동일 거래를 제외와 음수 취소 양쪽으로 중복 차감하지 않는다.

## 5. 검수·수정·충돌

처리상태(received/processing/processed/failed)와 검수상태(unreviewed/needs_review/user_checked/excluded)를 분리한다. processed는 OCR 실행 결과 상태이며 데이터의 정확성·세무 적격성을 뜻하지 않는다.

수정 요청은 기대 revision을 포함한다. 서버 revision과 다르면 모바일 수정과 PC 수정의 차이를 보여주고 다시 선택하도록 한다. 나중 요청의 무조건 덮어쓰기를 사용하지 않는다. 동일 수정의 재전송은 revision을 중복 증가시키지 않는다.

이미 내보낸 행의 수정은 새 revision을 만들고 기존 엑셀은 당시 스냅샷으로 남긴다. 현재 이력의 기존 엑셀을 조용히 덮어쓰지 않는다. 새 출력 시 변경된 행·수정버전을 표시한다. 실제 과거 재검수/재출력 기능은 현재 지원 범위 밖이므로 별도 구현 단위다.

별칭 학습은 [상호 설계](merchant_resolution_design.md)의 명시적 선택·작업공간 범위를 따른다. OCR 재실행이나 엑셀 다운로드만으로 새 별칭을 학습하지 않는다.

## 6. 날짜·월별 조회와 합계

- 거래일자를 기본 축으로 사용하며 거래시각이 없으면 date-only로 보존한다. 월 선택에 업로드일·생성일을 대신 쓰지 않는다.
- 수신/수정 시각은 timezone-aware UTC, 증빙의 거래일자·시각은 현지 표시와 시간대 근거를 분리한다. 한국 사업장 기본 시간대를 사용해도 assumed임을 남기고 원문 시각을 UTC로 오해하지 않는다.
- 날짜 미확인은 별도 목록에 남긴다. 월별 미확인 건수를 표시하고 임의의 월에 편입하지 않는다. 거래일자가 수정되면 최신 조회만 새 월에 배치하며 과거 출력 스냅샷은 유지한다.
- 필터는 기간·통화·거래구분·검수상태·포함상태·중복의심을 조합한다. 목록은 페이지 단위 조회하고 원본·대용량 사전을 매번 기기로 내려보내지 않는다.
- 합계 의미는 [통일 양식](receipt_standardization_proposal.md)을 따른다. 거래합계와 금전결제액을 각각 보여주며 포인트/상품권을 더해 다시 지출 합계로 만들지 않는다.
- 미검수·중복의심·부분 결제정보·금액 누락 건의 수와 알려진 소계를 별도로 표시한다. 추정 세액은 명시 세액 합계에 포함하지 않는다.
- 실제 월별 조회 인덱스는 `(scope_id, transaction_date, receipt_id)`, revision, operation 중복키, 관계 조회 등을 후보로 두고 합성 대량 데이터의 쿼리 계획으로 확인한다. 현재 DB의 대용량 상호 사전 조회와 거래 조회를 구분해 측정한다.

## 7. 보관·보안·삭제 경계

원본 파일은 단기 보관하고 가용상태(available/expired/deleted/missing)를 표시한다. 현재 문서상 파일 보관 기본값은 7일이고 cleanup은 수동 dry-run 기본이다. 자동 삭제가 이미 작동한다고 안내하지 않는다. DB·구조화값·출력물·기기 캐시·백업의 보관기간은 각각 정하고, 기간 정책을 정하기 전 무기한 저장을 전제로 공개 운영하지 않는다.

원본이 만료돼도 구조화 기록을 조용히 삭제하지 않으며, 원본을 다시 볼 수 없다는 점을 표시한다. 이용자의 증빙 보관은 별개이고 엑셀만으로 원본 보관을 대신한다는 표현을 쓰지 않는다. [국세청 세무 안내](https://t.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7802&mi=2480)

내부 ID·해시는 거래 연결용이며 엑셀에 접근 URL·전체 파일 경로·비밀키를 넣지 않는다. 장기 이력은 허용된 구조화 필드만 포함한다. 원본 재조회는 보관기간·접근권한을 확인해야 한다. 전화번호/주소는 허용된 사업장 필드에만 한정하며 로그에는 넣지 않는다.

## 8. 기존 자료와 단계별 전환

- A1 계약: 통일 양식·수정버전·수신 중복·저장 실패 정책을 합성 fixture로 정의한다. 실제 DB에 DDL을 실행하지 않는다.
- A2 로컬 신규 저장: 새 스캔의 미검수 기록 저장을 엑셀 생성과 분리하는 repository/service 작업을 한다. 스키마·UI·Exporter 변경은 분리하고 저장 실패 시 '저장됨'을 표시하지 않는다. 재시도는 같은 operation ID를 사용한다.
- A3 날짜별 조회: 신규 자료의 날짜별 목록·페이지 조회와 중복 후보 연결을 검증한다. 현재 작업별 이력·기존 파일 재다운로드는 유지한다.
- A4 기존 자료 이전: 별도 계획·백업·dry-run·동의된 범위로 진행한다. 기존 ID/job/source 관계를 보존하며 `total_amount`를 새 거래합계로 일괄 해석하지 않는다. 원래 revision·근거가 없는 값은 legacy_unknown으로 표시한다. 실제 고객 자료 재OCR이나 과거 엑셀 재생성을 자동 실행하지 않는다.
- A5 모바일 연계 실험: 비민감 샘플의 최소 구조화 전송파일로 receipt/operation ID 연결을 검증한다. 전체 StandardOCRResult·raw OCR·로컬 경로를 파일에 담지 않는다. 원본 비교가 필요하면 별도 명시적 전달과 단기 보관 범위를 정한다.
- A6 공개 서비스: 사용자 구분·인증·접근제어·동기화·보관/삭제 정책을 별도 구현·검증한다. 이 단계 전에는 로컬 서버를 다중 사용자용 서비스로 공개하지 않는다.

## 9. 수용 기준

동일 전송 재시도 3회가 거래 1건으로 끝나고, 같은 파일의 복수 영수증은 구역별로 유지돼야 한다. 다른 날짜 업로드가 기존 미검수 기록을 교체하지 않고, 새 OCR이 사용자 선택값을 덮어쓰지 않아야 한다.

서로 다른 기기의 동시 수정은 충돌로 드러나고, 전송 내용 변경·저장 실패·통신 중단 뒤 재시도도 중복 생성 없이 처리해야 한다. 날짜 미확인/수정·월경계·부분환불·중복 증빙·원본 만료·출력 후 수정·통화 혼합을 합성 데이터로 검증한다.

기존 이력 조회·기존 엑셀 재다운로드와 Parser/Validator/Exporter/end-to-end 회귀가 유지돼야 한다. 테스트에는 실제 고객 파일·네트워크·기본 pytest의 실제 OCR 실행을 포함하지 않는다. 다중 사용자 단계에서는 작업공간 간 접근 차단을 별도로 검증해야 한다.
