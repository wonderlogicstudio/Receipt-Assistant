# 상호 추출·사전 후보·사용자 검수 정리안

작성일: 2026-10-18. 상태: 설계 정리, 미구현.

이 문서는 [통일 양식 변경안](receipt_standardization_proposal.md)의 상호·사업장 식별 설계다. 현재 코드의 자동 보정, DB, Parser, Exporter를 변경하지 않는다. 특정 거래처 규칙 제거와 회귀 기준 변경은 후속 구현 단계에서 분리한다.

아래 현황은 2026-10-18 로컬 미커밋 소스 수정을 포함한 관측이다. 특정 치환 함수 등 일부 항목은 문서와 함께 커밋되지 않은 작업트리에만 존재할 수 있다. 규칙 이전 착수 시 실제 기준 커밋과 작업트리를 다시 구분한다.

## 1. 현재 경로와 문제

| 경로 | 현재 확인 내용 | 정리 방향 |
|---|---|---|
| `app/classifier/merchant_dictionary.py` | 사업자번호 매핑 30건, 상호 별칭 6건. 부분문자열로 특정 상호/지점명을 반환 | 출처가 있는 후보 데이터로 이동 검토. 부분 이름으로 지점 자동 선택 금지 |
| `app/parser/receipt_parser.py` | `_extract_merchant_name`, `_apply_standard_context_candidates`에서 고정 사전을 사용해 레코드 상호를 보정할 수 있음 | OCR 추출값과 사전 후보를 분리하고 기존 사용자 선택값을 보존 |
| `app/ocr/paddle_provider.py` | `_normalize_common_merchant_ocr_noise`의 특정 상호 치환, 특정 주유소 문맥 분기 등 | 일반 문자 정규화와 특정 거래처 지식 분리. Provider별 정답 사전 증식 방지 |
| `app/parser/normalizers.py` | 일반 상품/메타데이터 제외 규칙과 특정 상품 문구 제외 규칙이 함께 존재 | 일반 규칙은 유지 검증, 특정 문구는 사례 데이터로 목록화해 영향 확인 |
| `MerchantCandidateMatcher` | 사업자번호/별칭/유사상호/주소 힌트로 후보 반환. 후보는 검수 대상 | 공통 후보 검색 경로로 활용. 점수를 OCR 확률로 설명하지 않음 |
| 검수 화면 | DB 상위 후보와 점수를 표시하며 사용자가 상호를 수정 | 명시적인 후보 선택과 변경 근거 기록을 보완 |
| 검수 별칭 학습 | 엑셀 생성 시 일부 검수 입력값을 별칭으로 저장하는 코드 | 내보내기와 학습 분리. 사용자 선택과 사전 재사용 동의 범위를 기록 |

2026-10-18 읽기 전용 확인 당시 `data/` 아래 로컬 DB: merchant_master 2,694,552건, merchant_alias 0건. 데이터 양은 정확도·최신성·지점 구분 성능의 증거가 아니다. 다른 DB/실행환경에는 적용할 수 없는 관측값이다.

공공 상가정보에 사업자번호가 없으면 상호·주소 후보 사전으로만 사용한다. 상호 사전이 전체 사업자번호 원장이라는 가정이나 누락 번호를 임의 복원하는 규칙을 두지 않는다. 같은 파일의 `MERCHANT_CATEGORY_RULES`는 비용항목 추천 규칙이며 상호 식별·세무상 비용 인정 규칙과 구분한다.

## 2. 공통 상호 처리 흐름

```text
Provider -> StandardOCRResult -> StandardOCRParserContext
-> OCR 상호·사업자번호 후보 추출
-> 일반 정규화
-> 사전 후보 조회(사업자번호/상호/주소)
-> 충돌·지점 모호성 표시
-> 사용자 후보 선택 또는 직접 입력
-> ReceiptRecord 검수값 / 수정 이력 / 엑셀
```

Provider raw response/SDK 객체를 Parser·Matcher·Validator·Exporter에 전달하지 않는다. 현재 Azure의 제한된 호환 경로를 표준 경로로 전환하는 작업도 별도로 진행한다.

## 3. 값과 출처의 분리

| 데이터 | 보존할 내용 | 금지할 동작 |
|---|---|---|
| 추출값 | 허용된 상호 필드의 관측·정규화 값, block ID, OCR confidence | OCR 원문 전체를 별도 컬럼으로 저장 |
| 사전 후보 | master ID, 상호, 지점, 최소 지역 힌트, 매칭 방식, 유사도, 출처/기준일, 검토사유 | 후보를 OCR로 읽은 사실처럼 표시 |
| 사용자 선택값 | 선택한 후보/직접입력, 수정버전, 이유, 시각 | 사전 업데이트나 OCR 재실행으로 덮어쓰기 |
| 사업자번호 | 관측값·형식검사 상태·선택값 구분 | 형식 통과를 사업자 확인 또는 단일 지점 증명으로 사용 |

상호·연락처·주소를 공공 사전에서 얻었으면 `dictionary_candidate`로 표시한다. 영수증에 적힌 값으로 가장하지 않는다. 명시된 상호와 사전 후보가 충돌하면 두 출처를 유지하고 검토 사유를 남긴다.

## 4. 후보 우선순위와 충돌 규칙

1. 기존 사용자 선택은 유지한다. 새 OCR/DB 결과는 새로운 후보로만 추가한다.
2. 관측된 사업자번호와 일치하는 후보를 우선 제시하되, 여러 사업장·지점 또는 상호 충돌이 있으면 자동 선택하지 않는다.
3. 같은 작업공간에서 사용자가 선택한 별칭은 그 범위에서만 후보로 재사용한다. 사업자번호/지점 연결 근거가 없는 오인식 문자열은 다른 거래처에 전파하지 않는다.
4. 정규화 상호 완전일치도 동일 상호·다른 지점 가능성을 확인한다. 주소 힌트는 증거 보강용이며 영수증 주소값 자동 채움에 사용하지 않는다.
5. 유사도·부분일치·주소 단독 후보는 모두 검토 대상이다. 일치 점수 100도 정답 확률 100%나 사용자확인을 뜻하지 않는다.
6. 사업자번호가 다르거나 서로 다른 지점 근거가 있으면 `merchant_identity_conflict`; 여러 후보가 남으면 `merchant_branch_ambiguous`; 후보가 없으면 누락/저신뢰 사유를 표시한다. 최고 점수만으로 충돌 해소 금지.
7. 사업자번호 외부 상태 조회는 상태 참고 정보다. 영수증 상호, 주소, 거래 당시 상태, 세무 적격성을 보증하지 않는다.

## 5. 고정 규칙 분류와 이전 단계

| 분류 | 예 | 방침 |
|---|---|---|
| 일반 정규화 | Unicode·공백·구두점·사업자번호 표시 형식 | 동등성을 보존하는 범위에서 자동 적용. 명칭 의미·지점을 바꾸지 않음 |
| 일반 추출 규칙 | '상호명' 라벨, 명확한 상품/결제 메타데이터 제외 | 근거와 회귀 테스트로 관리 |
| 특정 거래처 지식 | 사업자번호→상호, 오인식명→상호, 브랜드→지점 치환 | 데이터로 분리하고 후보로 제시. 출처·범위·기준일 없는 항목은 legacy 후보로 제한 |
| 사례 전용 제외 | 특정 상품명·행사 문구 | 실제 영수증을 추가 수집하지 않고 합성 사례로 오탐·누락 영향 검증 |

- M1: 모든 특정 치환·부분일치 규칙의 위치, 적용조건, 출처 유무, 영향을 받는 합성 fixture를 목록화한다. 위 표는 시작 목록이며 전체 규칙 전수조사 완료를 뜻하지 않는다.
- M2: 추출값/후보값/검수값 계약과 충돌 테스트를 추가한다. 현재 결과 비교를 마련하고 기존 wrapper를 즉시 삭제하지 않는다.
- M3: 소수의 합성 거래처로 출처 있는 후보 사전 이전을 검증한다. 키·별칭 중복, 잘못된 지점 연결을 확인한다. 실제 고객 DB 일괄 변경은 하지 않는다.
- M4: 고정 사전의 자동 보정을 후보 반환으로 바꾸는 Parser 작업을 별도 수행한다. 검수 UI·별칭 학습·Exporter 변경도 분리한다.
- M5: 회귀 결과를 검토한 후 적용범위를 늘린다. 기존 테스트가 특정 상호 치환을 기대하면 새 후보/검수 계약으로 바꾸는 이유를 기록하며 기대값만 낮춰 통과시키지 않는다.

모든 미커밋 소스·fixture 수정은 보존한다. 원래 작업트리의 reset/stash/clean 없이 변경 단위를 분리한다.

## 6. 별칭 저장 정책

내보내기 버튼 자체를 학습 승인으로 사용하지 않는다. 사용자가 거래처를 선택·직접 수정한 행에서 별칭 후보와 재사용 범위를 확인하도록 설계한다. 제외 행, 미검수 행, 충돌 행, 전화번호/주소/상품명 같은 문자열은 별칭 저장 대상에서 제외한다.

별칭은 작업공간 ID, 연결 master/사업자번호/지점 근거, 별칭, 선택한 명칭, 출처, 버전을 가진다. 연결 근거가 부족하면 해당 거래의 검수값만 저장하고 공용 별칭을 만들지 않는다. 개인 작업공간의 별칭을 전체 고객 사전에 자동 합치지 않는다. 향후 다중 사용자 공개 운영은 별도 접근제어 설계·구현이 필요하다.

사전이 변경돼도 이미 검수한 거래의 상호·기존 엑셀을 자동 갱신하지 않는다. 재추천은 명시적 작업으로 수행하고 변경 전후 버전을 유지한다. 잘못된 별칭의 비활성화는 과거 검수 이력을 지우지 않는다.

## 7. 품질 기준과 회귀 범위

합성 평가에는 사전에 있는 거래처와 없는 거래처, 같은 브랜드의 다른 지점, 잘못 읽힌 사업자번호, 이름 일치/주소 충돌, 상품명이 상호처럼 보이는 사례, 지점 불명, 사용자가 이미 수정한 사례를 포함한다.

지표는 상호 추출 정답률, 지점 정답률, 후보 top-k 포함률, 잘못된 자동 치환 건수, 불필요한 질문/검토 건수, 사용자 수정량을 분리한다. 후보가 존재한다는 사실을 상호 정답으로 계산하지 않는다. DB에 없는 거래처를 평가에서 빼지 않는다.

Parser·merchant candidate·alias·민감정보 필터·검수 UI·Validator·Exporter·end-to-end 회귀를 확인한다. 실제 OCR/고객 파일/네트워크는 기본 pytest에 넣지 않는다. 출처를 알 수 없는 고정 사전은 정확도 평가의 정답 원장으로 사용하지 않는다.
