## 최종 요청과 이번 구현 범위

로컬 PaddleOCR → StandardOCRResult → StandardOCRParserContext → Parser 경로에서 이미 읽은 정보가 사라지거나 약한 금액 후보가 먼저 선택되는 원인을 수정한다. 기존 사용자 변경, 개인정보 제외, 명시 0과 미표기 구분, 표준 OCR 계약과 엑셀 구조를 유지한다. 사진 정답은 평가에만 사용하며 운영 코드에 전달하지 않는다. 유료 API·금액 역산·특정 영수증 정답 주입은 사용하지 않는다.

## 수정 파일과 구조

- `app/ocr/paddle_provider.py`: 허용된 신원 필드 분리, 제목 정규화, 기존 금액 후보의 라벨 우선순위 재검토, 원본 ROI 재인식. Parser에 SDK/raw output을 전달하지 않는다.
- `app/core/config.py`, `.env.example`: 선택적 `MERCHANT_LOOKUP_DB_PATH`. 검수 DB 경로와 분리한다.
- `app/db/database.py`, `app/db/merchant_repository.py`: SQLite 읽기 전용 연결. 조회 시 원본 사전 초기화·마이그레이션·쓰기를 하지 않는다.
- `app/ui/review_view.py`: DB 조회 후보의 출처와 선택 이유 표시, 선택한 상호만 검수 초안에 적용. 조회 시점과 다른 초안이면 오래된 후보를 숨긴다.
- `scripts/local_app.ps1`: V5만 기존 사전을 읽기 전용 조회한다. 기본 엔진 변경 없음.
- 새 테스트: `test_paddle_safe_identity.py`, `test_paddle_total_evidence.py`, `test_merchant_lookup_readonly.py`, `test_merchant_candidate_review_ui.py`. 기존 `test_local_app_launcher.py` 보완.
- 문서: 본 보고서와 README·PLAN·SPEC·CHECKLIST·CHANGE_CONTROL·DECISIONS.

인식 로직 변경은 Provider 단계에 한정했다. 이번 작업에서 Parser·ReceiptRecord·StandardOCRResult·ExcelExporter의 구조/버전은 바꾸지 않았다. 작업 시작 전부터 존재하던 넓은 변경·삭제 파일은 그대로 보존했다. 커밋·푸시는 하지 않았다.

## 평가 기준과 결과

기존 평가 파일 3개와 판독 기준은 바꾸지 않았다. 개발/문제 사진 17장을 처리했으나 기존 고정 기준이 있는 것은 **11장 × 8필드 = 88항목**이다. 기준 없는 6장을 포함해 136개 정답을 채점했다고 주장하지 않는다. 같은 거래의 재촬영 사진은 독립 검증으로 계산하지 않는다.

## 확인된 원인과 남은 조치

1. **민감정보 필터의 줄 전체 제외**: 같은 줄의 연락처 때문에 상호/사업자도 Parser에서 제외됐다. 마스킹된 줄에서 허용된 필드만 별도 블록으로 보존했다. 파생 블록 좌표는 원본 줄 범위이며 글자 단위 정밀 좌표는 아니다.
2. **제목과 이름 합침**: 제목 접두어 때문에 이름 후보가 제외됐다. 정규화만 분리하고 실제 이름은 읽은 문자열을 사용한다.
3. **약한 금액 후보의 선점**: 거래금액이 먼저 채워지면 총합계의 읽기 실패를 보완하지 않았다. 더 강한 명시 라벨을 비교하고 해당 숫자 행 전체를 재인식한다. 부분 숫자만 읽어 10원/600원으로 잘못 줄어드는 중간 실험은 폐기하고 행 전체 결합 및 강한 기존 근거 보호를 회귀 검증했다.
4. **사업자번호가 있으면 상호 재시도 생략**: 이름이 없을 때는 사업자 정보 주변 ROI를 추가 시도한다. 짧은 지점명 조각만 나온 경우 명시 상호 라벨이 없으면 채우지 않는다. 플레이월드는 재시도 후에도 누락되므로 해결됐다고 표시하지 않는다.
5. **DB 자료의 한계**: 기존 사전 2,694,552행 중 사업자번호가 기재된 행은 0개, 별칭도 0개였다. 번호 조회 구현이 있어도 대응 자료가 없다. 이름/주소 후보는 검수에 사용할 수 있지만 번호만으로 상호를 생성하지 않는다. 번호가 검증된 합법적 자료 확보나 사용자의 명시적 검수 등록이 후속 과제다.
6. **잘못 채워진 값과 주문표 구분**: 기존/별도 검증에서 총액 불일치가 남았다. 공급가액 누락도 다수다. 현재 추가 ROI가 해결하지 못했으므로 후보의 문서 영역/문서유형/라벨 연결을 다음 개발 단위로 분리해야 한다. 실패 사진을 개발용으로 쓰면 별도 검증 사진을 새로 선정해야 한다.
7. **문서 AI와 배포 부담**: 현재까지는 로컬 LLM을 필수 경로에 추가할 근거가 부족하다. 필요하면 익명 합성/새 독립 자료로 후보 제안 정확도·속도·메모리·모델 라이선스·설치 크기를 따로 검증하고, 원본 근거 검증 후 사용자 검수에만 제공한다. 이번에는 설치나 자동 보정 연결을 하지 않았다.
