# 세무사 전달용 영수증 통일 양식 변경안

작성일: 2026-10-18. 상태: 설계 정리, 미구현.

이 양식은 증빙 정리와 전문가 검토를 돕는 제품 내부 양식이다. 국세청 공식 신고서, 법정 장부 또는 공제 판단 결과가 아니다. OCR 결과는 항상 검수 대상이고, 비용항목은 추천, 증빙유형은 추정으로 표시한다.

이번 작업은 문서만 변경한다. 현재 `ReceiptRecord`, `StandardOCRResult`, Parser, DB, ExcelExporter, 버전값, 기존 8개 시트는 변경하지 않는다. 아래 필드명은 차기 계약 제안이며 현재 Python 속성명이 아니다.

현황 설명은 2026-10-18 로컬 작업트리의 미커밋 소스 수정까지 포함한 관측이다. 문서 커밋에 해당 소스 수정은 포함하지 않으므로 특정 현황 설명을 저장소 HEAD만의 동작으로 간주하지 않는다. 구현 여부는 관련 코드와 후속 테스트로 확인한다.

관련 설계: [상호 보정](merchant_resolution_design.md), [날짜별 누적 저장](receipt_accumulation_design.md). 현행 출력은 [현재 엑셀 구조](sample_output_schema.md)를 따른다.

## 1. 한 건의 의미와 공통 규칙

- 영수증 기록은 거래 후보 한 건이다. 사진 한 장, OCR 실행 한 번, 카드내역 한 줄을 각각 비용 한 건으로 더하지 않는다. 여러 증빙이 같은 거래를 나타내면 연결 관계를 관리한다.
- 거래처는 물품·서비스를 공급한 사업장이다. 결제대행사, 카드사, 구매자, 상품명과 구분한다. 실제 사업장명과 법인명이 다르면 각각 후보로 보존하고 지점을 임의 선택하지 않는다.
- 데이터 구조상 모든 칸을 정의하되 값은 비어 있을 수 있다. 미인식·미표기·충돌은 `null`과 사유로 구분한다. `0`은 근거 있는 0원에만 사용한다.
- 일자·상호·거래합계 누락/충돌은 핵심 검토 사유다. 연락처·주소 미표기만으로 다른 유효한 필드를 폐기하지 않는다. 사업자번호 누락/형식 오류는 별도 표시한다.
- 거래 시각이 없으면 자정이나 업로드 시각을 넣지 않는다. 금액에는 통화를 붙이며 원화는 정수 원으로 처리한다. 외화의 소수 금액과 통화는 보존하고 임의 환산하지 않는다.
- 날짜별 정리는 증빙의 거래일자 기준이다. 업로드일·검수일·결제내역의 처리일과 구분하며 세무상 귀속 시기는 결정하지 않는다.

## 2. 기본 필드 계약

| 표시 항목 | 제안 필드 | 입력·검수 원칙 |
|---|---|---|
| 영수증ID / 수정버전 | `receipt_id`, `revision` | 거래 후보의 지속 식별자. 재처리 때 새 거래로 늘리지 않음 |
| 거래일자 | `transaction_date` | 원문 또는 사용자가 확인한 날짜. 없으면 날짜미확인 |
| 거래시각 / 시간대 / 정밀도 | `transaction_time`, `transaction_timezone`, `time_precision` | 시각·시간대를 임의 보충하지 않음. 정밀도는 date/minute/second/unknown |
| 거래처명 / 지점 | `merchant_name`, `branch_name` | 추출값·후보값·사용자 선택값 분리. 사업자번호만으로 지점 확장 금지 |
| 사업자번호 | `business_number` | 텍스트로 저장해 앞자리 유지. 형식/체크섬 통과는 실재 사업자·공제 가능성의 증거가 아님 |
| 사업장 연락처 | `merchant_contact` | 영수증에 표시된 사업장 연락처만 대상. 개인 휴대전화·대표자 개인 연락처는 기본 제외 |
| 사업장 주소 | `merchant_address` | 영수증의 사업장 주소만 대상. 고객 배송지·주거지·직원 주소 제외 |
| 거래구분 | `transaction_kind` | purchase/refund/cancellation/unknown. 취소·환불은 원거래와 연결 |
| 통화 | `currency` | KRW 등 명시 통화. 지역 기본값을 쓰면 assumed 출처 표시, 혼합 통화 합산 금지 |
| 할인전금액 | `gross_amount` | 표시된 할인 전 금액. 상품 행의 중복 합계 주의 |
| 할인금액 | `discount_amount` | 가격 차감으로 확인된 합계. 결제수단인 포인트·상품권을 포함하지 않음 |
| 합계금액(거래합계) | `transaction_total` | 증빙에 표시된 거래 합계/결제대상금액. 비용 인정액·공제 대상액을 의미하지 않음 |
| 금액(당일 금전결제액) | `money_paid_amount` | 이 거래에 실제 적용된 카드+현금+계좌이체 금액. 포인트·상품권·선불잔액 사용은 별도 |
| 공급가액(명시) | `supply_amount_explicit` | 증빙에 표시된 금액을 보존. 포인트·카드 결제액으로 재계산하지 않음 |
| 부가세(명시) | `vat_amount_explicit` | 증빙에 표시된 값. 미표기는 `null`, 0원으로 간주하지 않음 |
| 면세금액 / 기타 명시금액 | `tax_free_amount_explicit`, `other_amounts_explicit` | 표시된 범위와 의미를 함께 기록. 세무 판단으로 새 금액을 만들지 않음 |
| 참고 추정공급가액·부가세 | `estimated_supply_amount`, `estimated_vat_amount` | 현행 참고값과 분리 보존. 새 양식에서는 기본 숨김, 명시값·월별 합계에 섞지 않음 |
| 증빙유형(추정) / 비용항목(추천) | `evidence_type_estimate`, `expense_category_recommendation` | 추천·추정 표시 유지. 사용자가 선택한 비용항목과 분리 |
| 사용목적 / 사용자 선택 비용항목 | `business_purpose_note`, `user_expense_category` | 사용자 입력. 세무상 비용 인정·공제 가능 여부를 자동 결정하지 않음 |
| 검수상태 / 검토사유 | `review_status`, `review_reasons` | 미검수/검토필요/사용자확인/제외. 사용자확인은 세무 검토 결과가 아님 |
| 출처 / 원본 가용상태 | `source_file_id`, `source_file_name`, `source_availability` | 파일명·불투명 ID만 표시. 절대경로·접근 URL 노출 금지 |

연락처·주소는 현재 최종 모델에 없고 전화번호 필터도 작동한다. 새 필드 도입은 허용된 사업장 필드만 명시적으로 처리하는 별도 변경으로 진행한다. 기존 민감 필터 전체를 완화하거나 DB/로그에 OCR 원문을 남기는 방식은 사용하지 않는다. 분류가 불명확한 연락처·주소는 비워 두고 검토 사유를 표시한다.

`money_paid_amount`는 이 거래 시점의 결제 정보다. 이전에 산 상품권의 구매대금, 나중 카드대금 납부, 세무상 경비를 뜻하지 않는다. 현금이 받은금액 20,000원/거스름돈 5,000원으로 명확히 표시되면 적용현금 15,000원은 산술 파생값으로 구분할 수 있다. 받은금액 자체를 결제액으로 더하지 않는다. 일부 결제수단 누락 시 부분합을 전체 금전결제액으로 표시하지 않고 미확인으로 둔다.

## 3. 포인트·상품권·할인·복합결제

결제 상세와 차감 상세는 한 거래에 여러 행을 허용한다. 카드 2장 결제도 각 행을 유지한다.

| 구분 | 기록할 내용 | 처리 규칙 |
|---|---|---|
| 결제 상세 `payment_components` | 수단, 적용금액, 통화, 출처, 근거ID, 확인상태 | card/cash/transfer/points/gift_certificate/prepaid/other/unknown |
| 차감 상세 `adjustments` | 유형, 차감금액, 할인합계 포함관계, 근거ID | 가격 할인으로 확인된 coupon/points/discount 등. 합계와 세부행 중복 가산 금지 |
| 포인트 사용 | `usage_role`=tender/discount/unknown, 포인트 수, 원화 환산 명시액 | 사용 포인트 수와 원 금액을 구분. 1P=1원 가정 금지 |
| 포인트 적립·잔액 | 선택적 참고 정보 | 사용금액·할인·결제합계에서 제외. 필요 없는 계정·멤버십 번호 저장 금지 |
| 상품권·선불잔액 사용 | 결제 적용액과 확인된 수단 | 가격 할인으로 자동 분류하지 않음. 상품권 구매 거래와 사용 거래 연결은 별도 검토 |

원문에 '포인트 사용'만 있으면 할인인지 결제수단인지 정하지 않는다. 금액 차이가 맞아도 역할을 임의 선택하지 않고 `point_role_unresolved`를 남긴다. 동일 포인트 항목을 할인과 결제 양쪽에 계상하지 않는다. 서로 다른 포인트 사용 항목이면 근거ID로 구분한다.

## 4. 산술 확인과 세무 판단의 경계

| 확인식 | 적용 조건 | 누락·충돌 시 |
|---|---|---|
| 할인전금액 - 중복 없는 할인 = 거래합계 | 같은 범위의 가격 항목이 모두 명시되고 별도 추가요금이 없음 | 미확인은 not_checkable, 불일치는 검토필요. 원문 금액 덮어쓰기 금지 |
| 결제수단별 적용액 합계 = 거래합계 | 결제 구성 완전성이 확인되고 모든 사용 항목의 역할·통화가 같음 | 포인트 역할 미확인/일부 수단 누락이면 일치 판정 금지 |
| 공급가액 + 부가세 + 면세금액 + 기타 명시항목 = 거래합계 | 항목들이 중복 없이 합계 전체를 설명한다는 근거가 있음 | 공급가액의 범위나 다른 세금·봉사료가 불명확하면 비교 보류 |
| 카드내역 금액 = 해당 카드 결제 적용액 | 카드 결제 행이 특정되고 통화·거래 관계가 맞음 | 포인트 포함 거래합계와 카드금액을 직접 비교해 오류로 판정하지 않음 |

차액은 자동 보정액이 아니다. 자동 허용오차로 값을 바꾸지 않는다. 원 단위 오차도 기록하고, 향후 통화별 허용오차가 필요하면 별도 규칙으로 정한다. 부가세 미표기에 일률적으로 10%를 적용하거나 면세로 분류하지 않는다. 원문 공급가액·세액이 금전결제액과 달라도 그대로 보존한다.

법령은 마일리지 유형과 거래 조건을 구분한다. 이 제품은 포인트의 과세표준 포함 여부를 판정하지 않는다. [부가가치세법 시행령 제61조](https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1032157081)

## 5. 합성 예시

아래는 양식과 산술 규칙 설명용 가상 사례다. 세무처리 예시가 아니다. 명시값이라고 적은 항목만 원문에 있다고 가정한다.

| 사례 | 할인전 / 할인 / 거래합계 | 결제 구성 | 당일 금전결제액 | 확인 사항 |
|---|---|---|---|---|
| 카드 단독 | 11,000 / 0 / 11,000 | 카드 11,000 | 11,000 | 공급 10,000·부가세 1,000이 명시된 경우만 각각 기록 |
| 할인+포인트 결제 | 20,000 / 2,000 / 18,000 | 카드 13,000 + 결제수단으로 표시된 포인트 5,000원 | 13,000 | 300P 적립은 합산 제외. 공급·부가세 미표기는 빈칸 |
| 포인트 할인 | 20,000 / 5,000 / 15,000 | 카드 15,000 | 15,000 | 명시된 포인트 할인 5,000은 할인 5,000의 세부항목. 두 번 차감 금지 |
| 상품권 전액 결제 | 20,000 / 0 / 20,000 | 상품권 20,000, 카드·현금 없음이 확인됨 | 0 | 합계가 0원이 아님. 공급·세액 추정 금지 |
| 전액 할인 | 10,000 / 10,000 / 0 | 추가 결제 없음이 명시됨 | 0 | 0원도 기록 유지, 자동 제외 금지 |
| 역할 불명 포인트 | 할인 불명 / 합계 20,000 | 카드 15,000, '포인트 사용 5,000원'만 표시 | 15,000 (그 외 금전수단 없음 확인 시) | 합계를 15,000으로 바꾸지 않음. 포인트 역할·구성 대조는 검토필요 |
| 현금·거스름돈 | 합계 15,000 | 받은현금 20,000 - 거스름돈 5,000 | 15,000 (산술 파생) | 현금 입력 20,000과 적용액 15,000 중복 합산 금지 |
| 과세·면세 혼재 | 합계 18,000 | 카드 18,000 | 18,000 | 명시 공급 10,000 + 세액 1,000 + 면세 7,000이면 범위 확인 후 대조 |

## 6. 세무사 전달용 엑셀 제안

현재 8개 시트의 실제 동작은 유지한다. 다음은 별도 Exporter 버전에서 검토할 표시안이다.

- `01_정리내역` 앞부분: 영수증ID, 거래일자, 거래시각, 거래처명, 사업자번호, 사업장연락처, 사업장주소, 금액(당일금전결제액), 공급가액(명시), 부가세(명시), 합계금액(거래합계).
- 뒷부분: 통화, 거래구분, 할인전금액, 할인금액, 포인트사용금액(명시환산액), 포인트역할, 상품권사용금액, 증빙유형(추정), 비용항목(추천), 사용자선택비용항목, 사용목적, 검수상태, 검토사유, 원본파일명, 원본가용상태, 수정버전. 서로 다른 역할의 포인트는 상세 시트로 구분하고 unknown을 합산 판정에 쓰지 않는다.
- 결제·차감 상세 시트 후보: 영수증ID를 기준으로 수단별 여러 행과 포인트 역할·근거·포함관계를 표시. 새 시트 도입은 별도 ExcelExporter 변경이다.
- 월별요약: 거래일자·통화별 구매합계/환불합계/표시순합계, 당일금전결제액, 명시 공급가액/부가세, 미검수건수, 미확인금액건수, 중복의심건수를 분리. 서로 다른 지표를 더해 지출 총액으로 만들지 않는다.
- 결측 금액은 0원으로 표시하지 않는다. 알려진 금액 소계와 미확인 건수를 함께 표시해 전체 합계처럼 보이지 않게 한다. 공급가액·세액의 출처가 다르거나 미확인인 건도 별도 건수로 표시한다.
- 검토필요 건은 검토필요 시트에서 추적한다. 01에는 사용자확인·포함 건을 두는 변경안을 제안하되, 현재 포함 규칙은 구현 단계에서 별도로 변경·회귀 검증한다. 미검수 건도 검토용 파일로 다운로드 가능하며 세무사 전달 준비 상태와 구분한다.
- 구매는 양의 크기, 환불·금액 취소는 양의 크기와 별도 방향으로 저장하고 표시순합계에서만 부호를 적용한다. 원문 음수는 관측값으로 보존한다. 구분 불명인 음수는 임의 절댓값 변환하지 않는다. 취소는 원거래와 연결 확인 전 순합계에 자동 반영하지 않는다.
- 동일 거래의 카드전표·상세영수증·세금계산서는 증빙 간 관계를 검토해 중복 계상 의심을 표시한다. 원본 증빙을 자동 삭제하거나 두 거래를 자동 병합하지 않는다.

## 7. 출처·검수·호환성

각 필드에는 관측값/정규화값/후보값/사용자선택값을 구분하는 메타데이터를 둔다. 출처 유형(ocr_explicit/user_input/dictionary_candidate/derived/legacy_unknown/assumed), OCR Provider·모델·Adapter·Parser·Validator 버전, 근거 block ID, 수정버전, 검토 사유를 관리한다. 원문 전체·raw JSON·민감값을 이력이나 근거 문자열로 우회 저장하지 않는다.

OCR confidence와 DB 유사도 점수는 서로 다른 값이며 정확도 확률로 합치지 않는다. 원본이 삭제된 뒤에도 구조화값과 근거ID는 남길 수 있으나 원본 재확인 불가 상태를 표시해야 한다.

현행 `total_amount`는 실제결제액 우선 선택 경로가 있어 새 `transaction_total`로 일괄 복사할 수 없다. `paid_amount`도 복합결제 전체의 금전결제액인지 재검토해야 한다. 기존 자료는 `legacy_unknown`으로 보존하고 사용자 재검수 없이 값을 재해석하지 않는다. 현행 추정 공급가액·부가세는 명시 필드로 이동하지 않는다.

`StandardOCRResult`는 내부 OCR 계약이고 외부 동기화/장기저장 문서 자체가 아니다. 전송·저장은 필드 허용목록으로 따로 정의하며 `provider_fields`, OCR text block 전체를 통째로 저장하지 않는다. Provider raw response는 Parser로 직접 전달하지 않는다.

## 8. 구현 순서와 수용 기준

1. 필드 의미·타입·금액 예시를 계약 테스트로 작성하고 현행 출력과 비교한다.
2. 연락처/주소 허용범위와 민감정보 비노출 테스트를 별도로 준비한다.
3. 신규 레코드·저장 계약, Parser 매핑, Exporter 변경을 분리한다. 실제 버전 변경 시 SPEC/CHECKLIST/fixture를 동기화한다.
4. 합성 사례로 카드 단독, 포인트 사용/적립/역할불명, 상품권, 전액 할인, 거스름돈, 혼합 세액, 복합 카드, 취소/부분환불, 외화, 시각 미표기, 금액 누락, 명시값 충돌을 검증한다.
5. Parser·Validator·Exporter·end-to-end 회귀와 기본 pytest(실제 OCR 제외)를 통과한다. 실제 OCR 품질은 정답이 있는 별도 opt-in 비교로 확인한다.

연락처·주소·거래시각이 누적 저장/검수/엑셀까지 보존되고, 포인트/상품권 때문에 합계나 세액이 임의 변경되지 않아야 한다. 테스트 통과는 OCR 정확도나 세무상 적격성의 증거가 아니다.

## 9. 증빙 보관과 외부 근거

앱의 원본 단기 보관과 이용자의 세무상 증빙 보관은 별개다. 앱이 원본을 정리해도 증빙 보관 의무가 사라지거나 엑셀만으로 원본을 대체한다는 안내를 하지 않는다. 이용자가 본인 저장소에 증빙을 보관·전달할 수 있게 하고 앱에는 가용상태를 남긴다. 구체적인 기간·예외는 해당 거래와 전문가 확인을 따른다. 국세청은 장부·증빙 보관과 예외 기간을 안내한다. [국세청 세무 안내](https://t.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7802&mi=2480)

카드로 결제했다는 사실만으로 매입세액 공제를 결정하지 않는다. 국세청도 사업용 카드 사용내역의 공제·불공제 확인 절차를 안내한다. 제품은 사용목적과 증빙값을 정리해 전달한다. [국세청 사업용 신용카드 안내](https://b.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7799&mi=2475)
