# 실제 영수증 8장·별도 4장 OCR 개선

2026-10-19. Ponytail full. 기존 미커밋 변경을 보존하고 Provider 검증 후 Parser 검증을 진행했다.

**100%는 달성하지 못했다. 기존 47개 기준은 39/47 → 40/47이며, 개발에 사용하지 않은 새 4장은 24/30 → 24/30이다. 기존 일치값 퇴행은 두 집합 모두 0개다.** 사용자가 지적한 별도 문제 사진 4장은 개발 자료로 구분해 18/29 → 25/29로 개선했다. 이 성적을 미사용 사진 성적으로 합치지 않는다.

## 1. 변경 파일과 구조

- `app/ocr/paddle_provider.py`: 명시된 같은 행 라벨·값을 기존 숫자 시퀀스보다 우선한다. 동순위 충돌은 후보와 출처를 보존한다. 대괄호 상호 라벨, 가맹점 식별번호와 상호 구분, 과세매출, 면세물품가액 제외, 위치 있는 세액 행의 다음 결제금액 차용 방지, 저신뢰 금액 후보 제외를 보완했다.
- 같은 파일: 최초 120블록에서 잘리던 경계를 2,048블록으로 늘렸다. 원본 행의 오른쪽 숫자를 별도 인식해 누락 공급가액·세액·할인을 보완한다. 이는 기존 Paddle 모델의 recognition-only 경로이며 새 모델/API가 아니다.
- `app/parser/normalizers.py`: 숫자가 이름에 붙어 있다는 이유만으로 상호 전체를 금액 메타데이터로 버리던 판정을 수정했다.
- `app/parser/receipt_parser.py`: 정규화 후 충돌하는 typed 후보를 검수 대상으로 비운다. 명시 final 후보가 있는 경우 더 큰 paid 후보로 총액/최종금액을 바꾸지 않는다. 기존 VAT 검수 힌트도 보존한다.
- `app/exporter/excel_exporter.py`, `tests/test_excel_exporter.py`: 실제 브라우저 대조에서 상호의 `/`를 경로로 오인해 지점명만 남기는 오류를 발견했다. 일반 상호 구분자는 보존하고 실제 절대경로·문장 속 경로·업로드 경로와 수식 보호는 유지한다. 합성 회귀의 수정 전 실패를 확인한 뒤 수정했다.
- `tests/test_paddle_explicit_evidence.py`, `tests/test_parser_evidence_selection.py`, `tests/test_paddle_numeric_rows.py`: 실제 사진과 다른 상호·번호·금액으로 일반 규칙을 검증한다.
- `tests/test_paddle_synthetic_quality_fixtures.py`: 서로 다른 명시 합계와 더 큰 결제 후보를 무조건 큰 값으로 바꾸던 기존 합성 기대값을, 합계 보존·불일치 경고 정책으로 변경했다. 실제 사진 정답 변경과 구분한다.
- README, PLAN, SPEC, CHECKLIST, CHANGE_CONTROL, DECISIONS와 이 보고서.

`StandardOCRResult → StandardOCRParserContext → ReceiptRecord → Validator → 검수/ExcelExporter` 경계를 유지한다. Parser에 Provider SDK/raw response를 전달하지 않았다. 모델/의존성/기본 Azure 설정/기존 DB/기존 엑셀 구조는 변경하지 않았다. 상호 DB 주입·별칭 자동 치환·누락 금액 계산은 추가하지 않았다.

## 2. 평가 기준과 독립성

로컬 기준·해시는 `output/quality_refs/quality12_frozen_manifest.json`에 보관한다. 원본과 정답은 Git에 넣지 않는다. 인식에는 `evaluation.jpg`라는 중립 표시 이름만 전달하며, 기대값은 인식이 끝난 후 평가 도구에서만 비교한다. 운영 `app`은 평가 기준을 읽지 않는다.

- 기존 8장의 이전 47개 양성 기준 `visual_reference.json`은 바꾸지 않았다. SHA-256: `bdfbc3275ebe0101e569cce62304c1b159d7de7b81876209a3bce067c1b23ecc`.
- 이번 8개 필드 확장 기준은 64필드 중 값 있는 49개·미표기 15개다. 공급가액 관찰 2개와 결제수단 미표기 1개를 추가했다. **기존 47개 성적과 구분**한다. 확장 49개 성적은 39 → 40이며, 추가 공급가액 2개도 실패 항목으로 유지했다. 해당 원문의 `금액`/`판매금액`을 공급가액으로 자동 해석하지 않아 명시 공급가액의 의미 확인도 남는다. 이 둘을 맞추려고 역산하거나 값을 채우지 않았다.
- 날짜는 현재 ReceiptRecord의 날짜 단위 계약을 유지한다. 시각까지 인식했다고 주장하지 않는다. 상호 비교는 기존과 같이 띄어쓰기·구두점만 무시하며, 지점 누락/다른 글자는 오답이다. 나머지 값은 정확히 일치해야 한다.
- `null`은 미표기, 숫자 0은 실제 인쇄된 0이다. 이번 선택 필드에 판독 불가로 제외한 항목은 0개이며, 미표기와 양성 일치는 별도로 집계한다.
- 별도 검증 4장은 파일 순서 13/14/20/23(0부터 센 순서)이다. 기존 8장·별도 문제 사진·이전 검증용 08~11과 구분했다. 같은 거래 재촬영 사진을 시각적으로 제외했다. 같은 업체의 다른 거래는 포함한다. 이번 코드 개선에 사용하지 않았다는 의미이며 모든 과거 작업에서 처리된 적 없다는 보장은 아니다.
- 문제 사진 4장은 바베큐, 청초수, GS25, 월정사다. 플레이월드는 기존 8장에 포함된다. 문제 사진의 성적은 개발 자료 성적이다.

### 기준 작성 실수와 재평가

문제 사진의 첫 기준에서 GS25 전화번호를 사업자번호로 옮긴 실수를 발견했다. 최초 파일을 덮어쓰지 않고 `quality12_problems_v2.json`으로 올바른 인쇄 위치·번호를 정정했다. 다른 정답/항목/사진은 바꾸지 않았다. 정정 기준으로 **보존한 이전 Provider·Parser와 최종 코드를 둘 다 재실행**했다. 정정 전 17/29와 정정 후 이전 코드 18/29를 구분한다. 정정 후 기준까지 코드 수정 전에 고정됐다고 주장하지 않는다. 기존 8장 기준과 새 별도 4장 기준은 변경하지 않았다.

### 남은 실패

- 기존 S01 공급가액·부가세: 인쇄된 0과 손상된/다중 행 라벨의 광학 인식 실패. 원본 행 인식·대비 보정으로도 안정적인 증거를 얻지 못했다.
- 기존 S02 상호·공급가액: 큰 제목/상호 결합과 지점 글자 오독, 오른쪽 0 인식 실패. 제목 영역 자르기와 행 분리 실험도 올바른 전체 상호를 회복하지 못했다.
- 기존 S03 상호: 지점 글자 누락/오독. 상단 크롭에서도 전체 상호를 회복하지 못했다.
- 기존 S04 합계·부가세: 합계 자릿수 및 세액 라벨/숫자 조합 오독. 총액의 0을 붙이거나 공급가액·세액으로 합계를 만들지 않았다.
- 확장 공급가액 2개: 위에서 밝힌 라벨 의미 확인 및 숫자/항목 연결 미해결. 기존 47개 기준에 몰래 편입/제외하지 않았다.
- 청초수 부가세: 숫자가 여러 조각/다른 자릿수로 읽혀 잘못된 8이 남는다. 명시 8,636을 읽은 것으로 보정하지 않는다.
- 월정사 날짜·공급가액·부가세: 날짜 일부 글자 오독과 명시 0 누락. 사전/다른 사진으로 보정하지 않는다.
- 미사용 H02 상호·번호·총액·공급가액, H04 상호·부가세는 불일치다. 최종 소스를 고정한 뒤 출처를 읽기 전용으로 확인했다. H02는 Provider가 상호 대신 카드 안내 조각을 후보로 만들고 Parser는 이를 거부했다. 사업자번호의 유효 후보도 없었다. 합계는 `10`·`00` 조각으로 읽혀 1,000원이 됐으며, 인쇄된 10,000원에 맞추려고 0을 추가하지 않았다. 공급가액에 해당하는 거래금액의 항목 연결도 남는다. H04 상호는 `솥`이 `솔`로 읽혔고, VAT 후보의 출처는 세액 행이 아닌 승인/할부 영역의 `관부`로 읽힌 조각이었다. **광학 오류뿐 아니라 세액 연결 오류도 남는다.** 이 결과에 맞춰 OCR/Parser를 다시 수정하지 않았다. 후속 개발에 쓰면 새로운 별도 검증 자료가 필요하다.

현재 모델에서 시도한 경로로 회복하지 못했다는 뜻이며, 사람이 못 읽는 사진 또는 영구적인 OCR 엔진 한계라고 단정하지 않는다. 같은 8장에 대한 개발 성적도 일반 인식 정확도가 아니다.

.venv-ocr\Scripts\python.exe -B output/run_quality12.py complete dev problems validation

로컬 측정 도구 `output/run_quality12.py`는 정답을 인식에 전달하지 않고 실행 후 비교하며 Git에서 제외된다. 원본 전후 소스는 `.venv/ocr-quality-12-before`에 보존했다. 이전 normalizer는 이번 한 줄 변경을 되돌린 별도 사본으로 재구성해 이전 Parser에만 연결했다. 현재 제품 파일을 되돌리지 않았다.

- 최종 전체 **933 passed, 3 skipped**, 경고 1,061개. 실제 OCR·네트워크는 기본 테스트에 넣지 않았다.
- OCR Python의 최종 관련 검증 **128 passed**, 경고 100개. OpenCV 숫자 영역의 행 경계 자체 검사도 이 환경에서 통과했다.
- 새 테스트는 수정 전 괄호 상호/충돌 금액/숫자 포함 상호/세액 연결 실패를 재현했다.
- 각 실제 사진의 Standard 결과를 앱의 처리·검증 함수에 전달해 파싱 값 보존을 확인했다. 16건 각각 표·서식 콤마·엑셀 숫자/빈칸이 같은지 assert를 통과했다. 마지막 평가 도구의 결과 저장에서 dataclass를 Pydantic처럼 직렬화한 오류가 있었으며 제품 오류와 구분해 도구를 수정했다. 이후 실제 앱 엑셀과 다시 대조한다.
- 최신 앱은 사전 안내 후 프로젝트 실행기로 재시작했다. 실제 브라우저 검증 결과와 파일은 아래와 같다.

### 실제 앱 검증 완료

- Chrome의 기존 localhost:8501 탭에서 PaddleOCR Local/GPU를 명시적으로 선택해 같은 16장을 업로드·처리했다. 외부 OCR API는 사용하지 않았다.
- 실제 팝업 16개를 이전/다음으로 순회해 DOM 입력값을 읽고 다운로드한 엑셀의 날짜·상호·사업자번호·결제수단·네 금액 필드 **128개를 대조해 모두 통과**했다. 엑셀은 기존 8개 시트이고 숫자는 숫자형/천 단위 콤마, 누락값은 빈칸, 명시 0은 0이다.
- 첫 비교에서 발견한 상호 슬래시 잘림은 회귀 테스트로 수정했다. 실행 중 앱이 옛 Exporter를 유지하는 것도 실제 다운로드로 확인해 사전 안내 후 재시작·같은 자료 재처리·재생성·재다운로드했다. 최신 검증 파일은 `output/quality_runs/quality12_browser_verified.xlsx`, 안전 요약은 `quality12_browser_verification.json`이다. 초기 잘못된 다운로드와 구분한다.
- UI 원본·서식 스크린샷은 `output/quality12_actual_popup.png`다. 실제 사진이며 합성 시안이 아니다. UI 레이아웃 코드는 이번에 바꾸지 않았다.
- 검증 과정에서 정상 앱 흐름의 신규 업로드·처리 이력이 생성됐다. 기존 이력/이전 엑셀은 자동 재작성하지 않았다. 초기 검증에서 만든 옛 출력도 최신 검증 파일과 구분한다.
- 최종 전체 **933 passed / 3 skipped**, 경고 1,061개. 경로 보호 추가 후 관련 **51 passed**도 확인했다. 인식 결과 자체는 Exporter 수정 전후 동일하며 표준 시트/컬럼을 바꾸지 않았다.
- 모든 검증과 저장 후 마지막 경로 보호 수정까지 적용하도록 사전 안내 후 앱을 다시 시작했다. 8501 running과 Chrome의 PaddleOCR Local/GPU 진단을 확인했고 새 작업 대기 상태로 두었다. 검증 세션의 업로드 목록은 초기화됐으며 최신 검증 엑셀과 이력은 보존된다. 구성 기본값 Azure는 바꾸지 않았다.

## 6. 문서와 남은 범위

표준 OCR 모델/context/ReceiptRecord/8개 엑셀 시트 및 버전값은 변경하지 않았다. 코드·실행 결과·미검증 범위를 README/PLAN/SPEC/CHECKLIST/CHANGE_CONTROL/DECISIONS에 함께 기록한다.

숫자 재인식은 라벨 최대 6개, 각 라벨의 단어 영역 최대 4개로 제한한다. 순수 숫자·신뢰도 0.97 이상·서로 같은 값이 있을 때만 누락값을 채운다. 여러 라벨에서 값이 다르면 채우지 않고 경고한다. 기존 후보는 덮어쓰지 않는다. 기존 회전/세액/날짜 fallback은 별도여서 문서 전체 최대 호출 수가 24라는 의미는 아니다. Paddle 3 API에서는 인식 전용 경로가 건너뛰어질 수 있으며 그 환경은 검증하지 않았다.

미사용 사진의 품질 향상은 입증하지 못했다. 금액 오답이 남아 자동 제출/자동 정산에 사용할 수준이라고 주장하지 않는다. 모바일·PDF·대량 동시 처리·새 OCR 모델·외부 서비스·과거 DB 일괄 정정·전체 저장소 리팩터링·커밋/푸시는 수행하지 않는다. 이후 미사용 4장의 실패를 개선에 활용하면 이 집합도 개발 자료로 바꾸고 새로운 검증 집합을 정해야 한다.
