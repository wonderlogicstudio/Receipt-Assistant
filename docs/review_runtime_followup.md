# 검수 화면 미반영·닫기·같은 행 재열기 점검

2026-10-19. Ponytail full. 기존 미커밋 변경을 보존하고 UI와 관련 회귀만 수정했다. 상호는 동일 8장을 현재 앱 처리 경로로 재확인했으며 Provider/Parser를 추가 수정하지 않았다.

## 1. 생성·수정 파일

- `app/ui/review_view.py`: 기본 상단 X와 닫힘 callback 활성화, 닫은 뒤 표 위젯 선택/포커스를 새로 생성, callback에 현재 위젯 key 전달.
- `tests/test_receipt_form.py`: native 닫기 설정과 표 위젯 갱신 회귀.
- `tests/test_review_view.py`: 현재 위젯 key를 통한 원래 행 ID 매핑 회귀.
- README, PLAN, SPEC, CHECKLIST, CHANGE_CONTROL, DECISIONS 및 이 보고서.

합성 시안·검증 이미지와 익명 상호 점검 결과는 Git에서 제외된 `output/`에 저장했다. 고객 사진·원문 OCR·DB·엑셀은 Git에 추가하지 않았다.

## 2. 확인한 원인과 수정

### 실행 화면 미반영

8501 서버는 오전 11:44에 시작됐고 UI/OCR 소스는 그 뒤 수정됐다. 확인 가능한 Chrome 두 탭에는 `File change / Rerun` 알림과 이전 UI가 남아 있었다. 두 탭은 기존 합성 테스트 자료이며 사용자 실제 8장 세션 그 자체로 확인한 것은 아니다. 한 탭의 Rerun으로 최신 표 문구와 셀 선택 모드가 반영됐지만, 별도 검증 서버에서는 reload만으로 변경된 dialog 설정이 반영되지 않고 서버를 재시작한 뒤에야 상단 X가 나타나는 경우도 확인했다. 현재 화면과 저장된 소스가 같다고 가정하면 안 된다.

이전 검증 보고서에서도 사용 중 서버를 재시작하지 않았다고 기록했으므로, 소스 개선과 사용자 실행 환경 반영을 구분해야 한다. 이후 사용자가 "지금 재시작"을 승인해 프로젝트 실행기로 8501을 종료·시작했고, running 상태와 실제 Chrome의 새 작업 화면을 확인했다. 미저장 세션은 초기화됐으며 저장된 DB·엑셀을 다시 쓰거나 기존 OCR 결과를 자동 보정하지 않았다. 재시작 후 기본 선택은 기존 설정인 Azure다. 앞선 39/47은 PaddleOCR GPU 평가이므로 다른 엔진의 화면 결과와 직접 비교하면 안 된다.

### 닫기 버튼

기존 팝업은 `dismissible=False`여서 상단 X와 ESC가 비활성화되고 하단 닫기에 의존했다. 최신 기존 CSS의 1280×600 합성 화면에서는 하단 닫기가 보였으므로 그 화면에서 하단 잘림을 재현했다고 주장하지 않는다. 사용자 증상에 대비해 플랫폼 기본 상단 X를 켜고 닫힘 callback을 기존 `_close_receipt_dialog`에 연결했다. 하단 닫기는 그대로 유지한다. X·ESC·바깥 영역 클릭으로 닫을 수 있으며 저장 전 초안은 같은 세션에서 보존한다. 저장 버튼을 누르기 전에는 표/엑셀의 값이 바뀌지 않는다.

### 같은 행 클릭·더블클릭

첫 셀 클릭은 팝업을 열었지만, 닫고 같은 셀을 더블클릭하면 브라우저의 기존 선택/포커스가 남아 새로운 선택 이벤트가 나지 않는 문제를 실제로 재현했다. 서버의 selection을 빈 배열로 쓰는 이전 방식과 그 배열만 검사하던 테스트로는 충분하지 않았다.

닫힘 callback이 표 revision을 증가시키고 새 key로 표를 렌더링하도록 최소 수정했다. 선택한 영수증 ID·서버 필터·초안은 유지한다. 새로운 표의 원래 행 위치를 동일하게 영수증 ID에 연결한다. 기존 상세 검수 열기 버튼도 유지한다. 같은 행의 단일 클릭과 더블클릭 재열기를 실제 Chrome에서 확인했다.

**제약:** 표를 새로 만들기 때문에 브라우저에서 지정한 헤더 정렬·열 폭·표 내부 스크롤이 초기화될 수 있다. 서버의 필터와 선택 영수증은 유지한다. 이를 보존하는 별도 표 구현은 추가하지 않았다.

## 3. 상호 재확인과 구조

사용자 파일명 목록은 기존 판독 기준의 첫 파일과 `_01`~`_07`에 해당한다. 동일 사진으로 PaddleOCR GPU → StandardOCRResult → 앱 Parser → ReceiptValidator 경로를 실행했다. 실제 이미지에서 읽은 결과를 사용했고 DB 후보나 정답표로 치환하지 않았다. 앱의 파일 저장·이력·엑셀 생성은 실행하지 않았다.

| 사진 | 상호 결과 |
|---|---|
| 첫 파일(S01) | 일치 |
| `_01`(S02) | 누락 |
| `_02`(S03) | 값은 있으나 지점명 오인식 |
| `_03`~`_07`(S04~S08) | 5장 모두 일치 |

총 **6/8 일치, 1개 오인식, 1개 누락**이다. 상호가 전부 사라지는 결과는 현재 로컬 앱 처리 경로에서 재현되지 않았다. 다른 결과가 보이면 실제 선택 Provider, 재처리 여부, 실행 버전의 대조가 필요하다. 현재 볼 수 있던 두 합성 탭의 Provider가 Mock이라는 사실을 사용자 실제 8장의 Provider였다고 확대 해석하지 않는다.

과거 코드에는 이 파일명 8개의 정답과 사업자번호→상호 치환이 있어 실제 읽기 성공처럼 표시됐던 문제가 있었다. 이를 제거한 뒤 드러난 오류는 남아 있다. 정답표를 되살리지 않고 공통 인식·추출 개선과 검수 후보를 구분해야 한다. 이번 UI 수정으로 상호 인식률이 높아졌다고 주장하지 않는다.

## 7. 추가 개선 우선순위와 남은 위험

1. S02의 상호/영수증 제목 겹침, S03의 지점명 글자 오류를 공통 영역 분리·재인식으로 다룬다. 파일명이나 사업자번호 정답표로 보완하지 않는다.
2. 미확인 상호는 기존 상호 찾기를 검수 후보로 활용하고 사용자가 원본을 보고 선택한다. 후보를 자동 인식값으로 바꾸지 않는다.
3. 같은 8장의 성적과 새 자료의 성적을 나누고, 초기화된 과거 결과를 새 OCR 결과처럼 취급하지 않는다. 세액·최종금액 오류도 별도로 남는다.
4. 화면 작업의 완료 확인에는 소스·단위 테스트뿐 아니라 실제 실행 서버의 적용·버전 일치를 포함한다.

모바일·다른 브라우저·아주 낮거나 좁은 창·대량 동시 처리는 이번에 검증하지 않았다. 긴 영수증 전체 보기의 작은 글씨와 OCR의 남은 오류는 사용자 검수가 필요하다. 원본·DB·기존 엑셀을 재작성하지 않았고 커밋·푸시·배포하지 않았다.
